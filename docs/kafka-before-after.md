# 📊 카프카(Kafka) 도입 전/후 아키텍처 비교 분석

본 문서는 **Ticket Stream** 프로젝트에서 4단계(결제 승인 및 Saga 보상 트랜잭션)까지 구축한 시점에서, **카프카 도입 전(v1 동기식 구조)**과 **카프카 도입 후(v2 이벤트 기반 구조)**의 실질적인 아키텍처 차이점과 이점을 심층 분석한 문서입니다.

---

## ❓ 문제의식: "결과가 똑같은데 왜 카프카를 쓸까?"

단일 사용자가 Postman으로 API를 1건씩 호출할 때는 카프카 도입 전이나 후나 최종 결과(좌석이 `SOLD`로 바뀌고, 주문이 `COMPLETED`로 저장되는 것)가 겉보기에 동일해 보입니다.

하지만 **대용량 동시 요청 환경에서의 트랜잭션 격리, 응답 속도, 장애 복구 능력(내결함성), 도메인 결합도** 관점에서는 완전히 다른 시스템입니다.

---

## 🔍 핵심 차이점 4가지 심층 비교

### 1. 트랜잭션 분리와 응답 속도 (Latency)

```
[v1: 동기 호출 방식]
클라이언트 ──(선점/결제 요청)──> 하나의 거대한 단일 트랜잭션 ──(순차 완료 대기)──> 클라이언트 응답 (느림)
                               ├─ 좌석 상태 검증 & 수정
                               ├─ PG 외부 결제 통신 (1~3초 소요)
                               ├─ 주문 상태 수정
                               └─ 결제 이력 저장

[v2: 카프카 이벤트 방식]
클라이언트 ──(선점/결제 요청)──> 핵심 로직만 처리 + 카프카 이벤트 전송 ──> 클라이언트 즉시 200 OK (수 ms)
                                                                 │
                                                    (백그라운드 비동기 처리)
                                                    ├─ OrderEventConsumer (주문 상태 완료)
                                                    └─ SeatEventConsumer  (좌석 판매 확정)
```

- **도입 전 (v1)**:
  - 선점 요청 시 `좌석 UPDATE`와 `가주문 INSERT`가 단일 트랜잭션으로 묶입니다.
  - 결제 요청 시 `외부 PG 통신`, `결제 내역 저장`, `주문 완료`, `좌석 판매 확정`이 한 스레드 안에서 모두 끝나야만 클라이언트에 응답(200 OK)을 반환합니다.
- **도입 후 (v2)**:
  - 클라이언트 요청 시 핵심 작업(선점 또는 결제 승인)만 수행한 뒤, **카프카에 메시지를 발행(Publish)하고 즉시 200 OK를 응답**합니다 (응답 시간 수 ms 내외).
  - 후속 작업(가주문 생성, 주문 확정, 좌석 SOLD 확정)은 백그라운드 Consumer가 비동기로 처리합니다.

---

### 2. 장애 격리 및 데이터 무손실 보장 (Fault Tolerance & Eventual Consistency)

- **도입 전 (v1)**:
  - 외부 PG 결제는 정상 승인되어 사용자의 카드에서 결제 대금이 빠져나갔으나, 직후 네트워크 순간 지연이나 DB 락으로 인해 `좌석 SOLD 처리` 중 에러가 발생하면?
  - 전체 트랜잭션이 롤백되거나 500 Internal Server Error가 발생하여 **"돈은 빠져나갔는데 티켓 예매는 실패/취소되는 치명적인 데이터 불일치"**가 발생합니다.
- **도입 후 (v2)**:
  - 결제 승인 후 `payment.completed` 이벤트가 카프카 브로커에 정상 커밋(Write-Ahead Log)되는 순간, **데이터는 절대 유실되지 않습니다.**
  - 설령 주문/좌석 서비스가 일시적으로 다운되거나 DB가 과부하 상태에 빠져도, 서버가 정상화되면 카프카 오프셋(Offset) 위치부터 메시지를 다시 읽어와 재처리하므로 **100% 최종 일관성(Eventual Consistency)**을 달성합니다.

---

### 3. 도메인 간 결합도 제거 (Decoupling & Single Responsibility)

- **도입 전 (v1)**:
  - `PaymentService`가 `OrderService`, `SeatService`를 직접 의존(DI)해야 하므로 강한 결합(Tight Coupling)이 발생합니다.
  - 비즈니스 요구사항이 추가되어 *"결제 완료 시 카카오톡 알림톡 발송"*, *"포인트 적립"*, *"영수증 이메일 발송"* 등을 붙이려면 매번 기존의 `PaymentService` 소스코드를 계속 수정해야 합니다 (OCP 원칙 위배).
- **도입 후 (v2)**:
  - `PaymentService`는 오직 **"결제가 성공했다"는 팩트(Event)만 카프카에 전송**하고 자기 역할을 종료합니다.
  - 알림톡 발송이든, 포인트 적립이든 `payment.completed` 토픽을 구독하는 Consumer만 별도로 추가하면 되므로, **기존 결제 코드는 단 1줄도 수정할 필요가 없습니다 (발행/구독 모델의 확장성).**

---

### 4. 트래픽 버퍼링 및 DB 부하 평탄화 (Traffic Buffering & Rate Leveling)

- **도입 전 (v1)**:
  - 티켓 오픈 순간 1만 명이 동시에 좌석을 잡으면 DB에 1만 번의 주문 생성이 동시에 꽂힙니다.
  - 순간적인 커넥션 요청 폭주로 인해 **HikariCP 커넥션 풀이 고갈되고, DB CPU가 100%에 도달하여 서버 전체가 마비**됩니다.
- **도입 후 (v2)**:
  - 초당 수십만 건을 버티는 카프카가 1만 건의 이벤트를 중간에서 스펀지처럼 흡수(버퍼링)합니다.
  - 컨슈머는 **DB가 감당할 수 있는 속도(소화 가능한 Rate)에 맞춰 차근차근 메시지를 가져와 DB에 반영**하므로 DB가 절대 죽지 않습니다.

## 📊 종합 비교 요약표

| 비교 항목 | 카프카 도입 전 (v1 동기식) | 카프카 도입 후 (v2 이벤트 기반) |
| :--- | :--- | :--- |
| **통신 방식** | 동기식 메서드 직접 호출 (In-Process Sync) | 비동기 메시지 발행/구독 (Event-Driven Async) |
| **사용자 체감 지연시간** | 길다 (모든 연관 작업이 끝나야 200 응답) | **극도로 짧다 (수 밀리초 이내 즉시 응답)** |
| **트랜잭션 범위** | 2개 이상의 도메인이 묶인 거대 트랜잭션 | **도메인별로 완전히 분리된 단일 트랜잭션** |
| **장애 전파 (전염성)** | 후속 작업 실패 시 전체 트랜잭션 롤백/에러 | **장애 격리 (카프카 큐 보존 ➡️ 재시도 복구)** |
| **도메인 결합도** | 높음 (`PaymentService`가 Order, Seat 모두 의존) | **완전 분리 (이벤트 기반 느슨한 결합)** |
| **기능 확장성** | 새 기능 추가 시 기존 서비스 코드 수정 필요 | **신규 Consumer만 추가하면 끝 (기존 코드 무수정)** |
| **DB 부하 제어** | 스파이크 트래픽이 DB로 직격 (커넥션 고갈 위험) | **카프카가 트래픽 완충 후 순차 처리 (DB 보호)** |

## 🎯 5단계(Redis 대기열)와의 시너지 효과

> **"카프카는 내부의 고성능 엔진과 안전망을 완성한 것이고, Redis 대기열은 외부의 폭주 트래픽을 통제하는 게이트입니다."**

- **4단계까지 (카프카 도입)**:
  - 시스템 내부 파이프라인의 **비동기화, 장애 격리, 데이터 무손실, 결합도 분리**를 완벽하게 구축했습니다.
- **5단계 (Redis 대기열 부착)**:
  - 이제 입구에서 수만 명의 접속자를 Redis ZSet으로 줄 세우고, 초당 N명씩만 이 카프카 파이프라인으로 통과시킵니다.
- **최종 결과**:
  - v1은 k6 부하 테스트 시 100명만 몰려도 DB 락 타임아웃과 500 에러가 쏟아졌지만,  
  - v2는 **Redis 대기열(외벽 방어) + Kafka 파이프라인(내벽 고속 처리)의 2중 구조**를 통해 수천~수만 명의 동시 요청에도 **에러율 0%**로 완벽하게 버텨내게 됩니다.
